# Agent 范式对比：ReAct vs Plan and Execute vs Reflection

## 概述

AI Agent 有三种主要的执行范式，各有优缺点，适用于不同场景。

---

## 一、三种范式详解

### 1. ReAct (Reasoning + Acting)

```
用户输入
    ↓
┌─────────────────────────────────┐
│  思考: 我需要做什么               │
│  行动: 调用工具                   │
│  观察: 查看结果                   │
│  思考: 接下来怎么做               │
│  行动: 调用工具                   │
│  ...                            │
└─────────────────────────────────┘
    ↓
输出结果
```

**核心思想**：交替进行推理（Reasoning）和行动（Acting）

**执行流程**：
1. **思考**：分析当前状态，决定下一步
2. **行动**：调用工具执行操作
3. **观察**：查看工具返回的结果
4. **循环**：基于观察结果继续思考

**特点**：
- ✅ 简单直接，无需预先规划
- ✅ 即时反馈，用户可以随时介入
- ✅ 灵活性高，可以随时调整方向
- ❌ 缺乏全局规划，可能走弯路
- ❌ 不适合复杂的多步骤任务

**适用场景**：
- 简单任务：读取文件、修改代码、回答问题
- 即时交互：需要快速响应
- 探索性任务：不确定下一步做什么

---

### 2. Plan and Execute

```
用户输入
    ↓
┌─────────────────────────────────┐
│  Phase 1: 规划                   │
│  - 分析任务                      │
│  - 拆分为子任务                  │
│  - 确定依赖关系                  │
│  - 生成任务列表                  │
└─────────────────────────────────┘
    ↓
┌─────────────────────────────────┐
│  Phase 2: 执行                   │
│  [✓] 任务 1                      │
│  [→] 任务 2 ← 当前               │
│  [ ] 任务 3                      │
│  [ ] 任务 4                      │
└─────────────────────────────────┘
    ↓
输出结果
```

**核心思想**：先规划，再执行；分阶段完成任务

**执行流程**：
1. **规划阶段**：
   - 分析用户的整体任务
   - 拆分为可执行的子任务（2-10 个）
   - 确定任务之间的依赖关系
   - 生成 JSON 格式的任务列表

2. **执行阶段**：
   - 逐个执行任务
   - 更新任务状态（pending → in_progress → completed/failed）
   - 检查依赖关系，确保前置任务完成
   - 任务失败时停止后续执行

**特点**：
- ✅ 全局规划，避免走弯路
- ✅ 支持依赖关系，任务有序执行
- ✅ 可以预览计划，用户确认后再执行
- ✅ 支持并行执行无依赖的任务
- ❌ 规划阶段耗时
- ❌ 不够灵活，调整计划成本高

**适用场景**：
- 复杂任务：重构模块、迁移代码、添加新功能
- 多步骤任务：需要协调多个子任务
- 需要预览：先看计划，再决定是否执行

---

### 3. Reflection (反思)

```
用户输入
    ↓
┌─────────────────────────────────┐
│  生成初始输出                     │
└─────────────────────────────────┘
    ↓
┌─────────────────────────────────┐
│  评估: 这个输出好吗？             │
│  - 检查正确性                    │
│  - 检查完整性                    │
│  - 检查质量                      │
└─────────────────────────────────┘
    ↓
┌─────────────────────────────────┐
│  改进: 如何优化？                 │
│  - 修复问题                      │
│  - 增强内容                      │
│  - 重新生成                      │
└─────────────────────────────────┘
    ↓
循环直到满意
    ↓
输出结果
```

**核心思想**：生成 → 评估 → 改进，循环迭代直到满意

**执行流程**：
1. **生成**：创建初始输出
2. **评估**：检查输出质量
   - 正确性：是否有错误？
   - 完整性：是否遗漏内容？
   - 质量：是否达到标准？
3. **改进**：基于评估结果优化
4. **循环**：重复评估和改进，直到满意

**特点**：
- ✅ 质量高，自我纠错
- ✅ 适合创作任务，多轮改进
- ✅ 可以设定质量标准
- ❌ 耗时长，可能多次循环
- ❌ 可能陷入无限循环
- ❌ 需要明确的评估标准

**适用场景**：
- 高质量输出：代码生成、写作、设计
- 允许耗时：不急于立即完成
- 需要迭代：多次改进才能满意

---

## 二、范式对比总结

| 特性 | ReAct | Plan and Execute | Reflection |
|------|-------|------------------|------------|
| **规划能力** | ❌ 无 | ✅ 强 | ❌ 无 |
| **执行方式** | 线性 | 分阶段 | 循环迭代 |
| **灵活性** | ✅ 高 | ❌ 低 | ❌ 低 |
| **质量** | 中等 | 中等 | ✅ 高 |
| **速度** | ✅ 快 | 中等 | ❌ 慢 |
| **复杂度** | ✅ 简单 | 中等 | 中等 |
| **适用任务** | 简单/交互 | 复杂/多步骤 | 创作/高质量 |

## 三、Claude Code 和 Codex 的范式分析

### Claude Code

**主要范式：ReAct**

```
用户输入: "重构认证模块"
    ↓
Claude Code:
1. 思考: 需要先了解现有代码结构
2. 行动: read_file("src/auth.ts")
3. 观察: 看到代码结构
4. 思考: 需要设计新的接口
5. 行动: write_file("src/auth-new.ts", ...)
6. 观察: 文件创建成功
7. 思考: 需要更新路由
8. 行动: edit_file("src/routes/user.ts", ...)
... 交替进行，直到完成
```

**特点**：
- 以 ReAct 为主，边想边做
- 没有显式的任务列表
- 每一步都基于当前状态决策
- 简单直接，适合大多数任务

**为什么选择 ReAct**：
1. **简单直接**：用户输入后立即开始工作，不需要等待规划阶段
2. **交互性强**：支持即时反馈，用户可以随时介入
3. **灵活性高**：可以随时调整方向，不需要重新规划
4. **适合大多数任务**：简单任务 ReAct 足够，复杂任务通过多轮对话完成

---

### OpenAI Codex (CLI 版本)

**主要范式：ReAct**

```
用户输入: "添加用户认证功能"
    ↓
Codex:
1. 思考: 需要创建认证中间件
2. 行动: 创建文件
3. 观察: 文件创建成功
4. 思考: 需要添加路由
5. 行动: 修改路由文件
... 交替进行
```

**特点**：
- 纯 ReAct 模式
- 没有显式的 Plan 阶段
- 每一步都是即时决策

### 对比总结

| 特性 | Claude Code | Codex | zguigo |
|------|-------------|-------|--------|
| **主要范式** | ReAct | ReAct | ReAct + Plan and Execute |
| **任务规划** | 隐式（边想边做） | 隐式 | 显式（/plan 命令） |
| **任务列表** | ❌ 无 | ❌ 无 | ✅ 有 |
| **依赖管理** | ❌ 无 | ❌ 无 | ✅ 有 |
| **并行执行** | ❌ 无 | ❌ 无 | ✅ 支持（未来） |
| **反思机制** | ❌ 无 | ❌ 无 | ❌ 无 |

## 四、zguigo 的范式设计

### 1. 双模式支持

zguigo 同时支持两种范式：

**ReAct 模式（默认）**：
```
用户: "看看 src/index.ts"
zguigo: [立即读取并展示]
```

**Plan and Execute 模式（/plan）**：
```
用户: /plan 重构认证模块
zguigo: 
📋 正在生成任务计划...
✓ 任务计划已生成，共 5 个任务

  1. 分析现有认证代码
  2. 设计新的 Auth 模块接口
  3. 实现 JWT 验证逻辑
  4. 更新用户路由
  5. 运行测试验证

用户: /run
zguigo: [按计划执行任务]
```

### 2. 混合使用

```
用户: /plan 添加用户认证功能
zguigo: [生成任务列表]

用户: /run
zguigo: [执行任务 1]

用户: "等等，先看看现有代码结构"
zguigo: [切换到 ReAct 模式，读取文件]

用户: /run
zguigo: [继续执行任务 2]
```

### 3. 何时用哪种范式

**用 ReAct（默认）**：
- ✅ 简单任务：读取文件、修改代码、回答问题
- ✅ 即时反馈：需要快速响应
- ✅ 交互式：用户随时可能改变主意
- ✅ 探索性：不确定下一步做什么

**用 Plan and Execute（/plan）**：
- ✅ 复杂任务：重构模块、迁移代码、添加新功能
- ✅ 多步骤：需要协调多个子任务
- ✅ 依赖关系：任务之间有先后顺序
- ✅ 需要预览：先看计划，再决定是否执行

## 七、总结

| 范式 | 优点 | 缺点 | 适用场景 |
|------|------|------|----------|
| **ReAct** | 简单、快速、灵活 | 缺乏全局规划 | 简单任务、交互式 |
| **Plan and Execute** | 全局规划、支持依赖 | 规划耗时、不够灵活 | 复杂任务、多步骤 |
| **Reflection** | 质量高、自我纠错 | 耗时长、可能循环 | 创作任务、高质量需求 |

**Claude Code 和 Codex** 主要采用 **ReAct**，因为：
1. 简单直接，用户体验好
2. 支持即时反馈和交互
3. 适合大多数编程任务

**zguigo** 同时支持 **ReAct + Plan and Execute**，既有 ReAct 的灵活性，又有 Plan and Execute 的规划能力，是更完整的解决方案。
