# zguigo Agent CLI 设计

## 1. 项目定位

`zguigo` 是一个使用 TypeScript 和 Node.js 编写的、面向学习 Agent 原理的终端 AI 编程助手。产品定位参考 Claude Code，但采用从小到大的实现路线：先建立清晰、可调试的 Agent Loop，再逐步增加文件修改、命令执行、权限控制和更复杂的上下文管理。

第一阶段的目标不是做完整的编码代理，而是完成一个可运行、可观察、可测试的最小闭环。

## 2. 第一阶段范围

### 2.1 用户入口

```text
zguigo
zguigo "分析当前项目的入口文件"
zguigo --debug
```

- `zguigo` 启动交互式 REPL。
- 带任务参数时执行一次任务并退出。
- REPL 内置 `/help`、`/clear`、`/exit`，也支持 `Ctrl+C` 退出。
- 普通文本交给 Agent；以 `/` 开头的输入由 CLI 自身处理。

### 2.2 模型能力

第一版通过 OpenAI 兼容接口接入模型。既可以连接 GPT，也可以连接实现兼容协议的其他云端或本地模型。

配置变量：

```text
LLM_API_KEY
LLM_BASE_URL
LLM_MODEL
```

可选加载项目根目录的 `.env`，但 `.env` 必须加入 `.gitignore`，任何日志都不得输出 API Key。适配层应隐藏不同供应商在流式事件和工具调用细节上的差异；不支持流式的服务退化为一次性响应。

### 2.3 工具

只提供两个只读工具：

- `list_files`：查看 workspace 文件结构。
- `read_file`：读取指定文本文件。

工具访问范围是 CLI 启动时的当前工作目录及其子目录。必须解析路径并检查其仍位于 workspace 根目录内，拒绝 `..` 穿越。默认跳过 `.git`、`node_modules`、`dist`、`build` 等目录；单文件读取上限为 200 KB；二进制文件不按文本读取；异常以结构化工具错误返回给模型，不直接使进程崩溃。

第一版明确不支持写文件和执行 Shell 命令。

## 3. Agent Loop

```text
用户输入
  -> 写入 messages
  -> 调用模型（支持流式输出）
  -> 若为文本回答：输出并结束
  -> 若为工具调用：校验参数
  -> 执行只读工具
  -> 将 tool result 写回 messages
  -> 再次调用模型
```

约束：

- 默认最多 8 轮模型调用。
- 纯文本回答立即结束。
- 工具参数错误回传给模型，使模型有机会修正。
- 同一工具调用持续失败时可以提前终止。
- 达到上限时向用户说明任务已停止，并保留调试信息。
- 当前会话历史只保存在内存中；`/clear` 清空上下文；退出后不持久化。

建议将每轮循环建模为显式状态，而不是把所有逻辑塞进 CLI 入口：`messages`、`iteration`、`pending tool calls`、`last error` 和 `final answer` 都应可观察。

## 4. 建议模块边界

```text
src/
  cli/             命令行参数、REPL、内置命令、终端渲染
  agent/           Agent Loop、消息状态、循环上限、停止条件
  model/           OpenAI 兼容客户端、流式事件归一化、配置校验
  tools/           工具协议、list_files、read_file、路径安全
  workspace/       workspace 根目录、文件过滤和文本判断
  errors/          可识别的配置、模型、工具错误
```

依赖建议：

- TypeScript + Node.js
- 官方 OpenAI Node SDK（通过 `baseURL` 支持兼容服务）
- `Vitest` 用于测试
- 一个成熟的 CLI 参数/终端交互库（按实现时的依赖偏好选择）

模型层只暴露项目自己的最小接口，例如普通请求和流式事件迭代；Agent 层不直接依赖供应商 SDK 类型。工具层只接收结构化参数并返回结构化结果。

## 5. 调试与可观测性

默认只显示自然的流式回答。`--debug` 开启后把信息写入 `stderr`，包括：

- 每轮消息类型和摘要
- 工具名、参数、执行耗时和结果大小
- 循环编号
- 模型停止原因
- 供应商错误或错误堆栈

调试信息不能泄漏密钥，也不应把大段文件内容重复打印到终端。

## 6. 测试与验收

使用 mock 模型客户端，不让自动化测试依赖真实 API。第一阶段至少覆盖：

- `read_file` 的路径越界、文件过大、二进制文件
- `list_files` 的目录过滤
- 模型响应和流式事件解析
- 工具调用成功与失败
- 工具错误回传模型后的下一轮
- 达到 8 轮上限时的停止行为
- `/clear`、`/exit` 和一次性命令入口

手动验收需要使用真实兼容模型确认：流式文本显示、工具调用后继续回答、缺少配置时的清晰提示，以及 `--debug` 输出与普通输出分离。

## 7. 分阶段学习路线

### 阶段 0：工程骨架

初始化 TypeScript 项目、构建脚本、`zguigo` bin 入口、Vitest 和基础错误处理。学习重点：Node CLI 生命周期、编译产物和可执行入口。

### 阶段 1：单轮模型调用

读取环境变量，完成一次普通请求和流式文本输出。学习重点：消息结构、异步迭代器、供应商适配层。

### 阶段 2：内存会话与 REPL

加入 `messages`、REPL、`/help`、`/clear`、`/exit`。学习重点：会话状态和用户交互边界。

### 阶段 3：最小 Agent Loop

实现停止条件、8 轮上限和可测试的循环状态。学习重点：Agent 与普通聊天请求的区别，以及循环为何必须有边界。

### 阶段 4：只读工具

实现工具协议、`list_files`、`read_file` 和路径安全。学习重点：模型如何选择工具、tool result 如何回到消息历史。

### 阶段 5：调试与测试

加入 `--debug`、mock 模型和边界测试。学习重点：可观测性、确定性测试和错误恢复。

### 后续阶段

按风险递增：文件编辑（先生成 diff，再经用户确认写入）、Shell 命令（权限确认和超时）、Git 感知、会话持久化、上下文压缩、并行工具调用、MCP，以及更细粒度的权限和沙箱。

## 8. 暂不解决的问题

- 自动修改文件
- Shell 命令执行
- 多供应商原生协议的全部差异
- 会话持久化和上下文压缩
- 并行 Agent、子 Agent 和 MCP
- 完整的权限系统和生产级沙箱

这些能力不是被忽略，而是留到最小循环通过测试并且你已经理解其消息流转之后再引入。

## 9. 第一阶段完成定义

在任意项目目录执行 `zguigo`，配置有效的 OpenAI 兼容模型后，用户可以连续提问；模型能在需要时调用两个只读工具，工具结果能进入下一轮模型请求，回答以流式方式显示；路径越界和异常不会突破 workspace 边界；`--debug` 能解释循环过程；核心行为由不依赖真实 API 的测试覆盖。
